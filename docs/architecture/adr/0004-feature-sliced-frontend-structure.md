# ADR 0004: Feature-Sliced Architecture for Frontend

## প্রেক্ষাপট (Context)
প্রথাগত লেয়ার-বেসড কাঠামোতে সব কম্পোনেন্ট এক `components/` ফোল্ডারে, সব হুক এক `hooks/` ফোল্ডারে এবং সব পেজ এক `pages/` ফোল্ডারে থাকে। অ্যাপ বড় হলে কোনো একটি ফিচারের (যেমন নোটিশ বা ভর্তি) ফাইলগুলো খুঁজে পাওয়া অসম্ভব হয়ে পড়ে এবং ডেভলপাররা দুর্ঘটনাবশত অন্যান্য ফিচারের ডেটা ভেঙে ফেলে।

## সিদ্ধান্ত (Decision)
আমরা **Feature-Sliced Architecture** নীতি গ্রহণ করেছি:
- প্রতিটি ব্যবসায়িক ডোমেন `apps/web/src/features/{feature}/` ফোল্ডারে সীমাবদ্ধ থাকবে।
- প্রতিটি ফিচারের ভেতরে থাকবে:
  - `public/`: পাবলিক সাইটে প্রদর্শিত অংশ (UI component & modal).
  - `admin/`: অ্যাডমিন পোর্টালে প্রদর্শিত অংশ (manager/publisher).
  - `api.ts`: TanStack Query hooks.
  - `model.ts`: ফিচারের টাইপ ও ছোট ফাংশন।
  - `schema.ts`: Zod ভ্যালিডেশন স্কিমা।
  - `index.ts`: পাবলিক ব্যারেল এক্সপোর্ট।

অন্যান্য ফিচার শুধুমাত্র `index.ts` দিয়ে যোগাযোগ করতে পারবে; সরাসরি অভ্যন্তরীণ ফাইল ইম্পোর্ট নিষিদ্ধ।

## বিকল্প বিবেচনা (Alternatives Considered)
1. **Flat Layers (controllers/views/models):** স্কেল করতে পারে না।
2. **Atomic Design:** খুব বেশি ফাইল স্তর তৈরি করে এবং ব্যবসায়িক লজিকের সাথে খাপ খায় না।

## ফলাফল ও প্রভাব (Consequences)
- **ইতিবাচক:** উচ্চ মডুলারিটি, পরিষ্কার দায়িত্ব বিভাজন, এবং কোড রিভিউ অত্যন্ত দ্রুত হয়।
- **নেতিবাচক:** ফিচারের সংখ্যা বাড়লে প্রাথমিক ফোল্ডার সংখ্যা বেশি মনে হতে পারে।
