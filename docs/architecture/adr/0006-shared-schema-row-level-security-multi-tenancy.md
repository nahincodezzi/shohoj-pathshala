# ADR 0006: Shared Database with PostgreSQL Row-Level Security (RLS) Multi-Tenancy

## প্রেক্ষাপট (Context)
সহজ পাঠশালা শত শত স্কুলকে এক প্ল্যাটফর্মে হোস্ট করবে। স্কুলের ডেটা আইসোলেশন তিনভাবে করা যায়:
1. ডাটাবেস পার টেন্যান্ট (Database-per-tenant)
2. স্কিমা পার টেন্যান্ট (Schema-per-tenant)
3. শেয়ার্ড ডাটাবেস উইথ রো-লেভেল সিকিউরিটি (Shared schema with RLS)

## সিদ্ধান্ত (Decision)
আমরা **Shared Schema with PostgreSQL Row-Level Security (RLS)** নির্বাচন করেছি:
- প্রতিটি টেন্যান্ট-টেবিলে `school_id` কলাম থাকবে।
- কানেকশন শুরুতে টেন্যান্সি মিডলওয়্যার `SET LOCAL app.current_school_id = :school_id` এক্সিকিউট করে।
- ডেটাবেস ইঞ্জিন নিজেই পলিসি এনফোর্স করে যাতে কোনো ভুল কুয়েরিতেও অন্য স্কুলের ডেটা লিক না হয়।
- ব্যাকএন্ড রিপোজিটরির বেস ক্লাস স্বয়ংক্রিয়ভাবে `school_id` ইনজেক্ট করে (দ্বি-স্তরীয় প্রতিরক্ষা)।

## বিকল্প বিবেচনা (Alternatives Considered)
1. **Database-per-tenant:** ৫০০ স্কুলের জন্য ৫০০টি ডেটাবেস মেইনটেইন করা, মাইগ্রেশন চালানো এবং সার্ভার রিসোর্স খরচ অত্যন্ত ব্যয়বহুল। (বাতিল)।
2. **Schema-per-tenant:** কানেকশন পুলিং এবং ক্রস-টেন্যান্ট রিপোর্টিং অত্যন্ত জটিল। (বাতিল)।

## ফলাফল ও প্রভাব (Consequences)
- **ইতিবাচক:** সর্বোচ্চ সার্ভার এফিশিয়েন্সি, সহজ সেন্ট্রাল ব্যাকআপ ও মাইগ্রেশন, এবং PostgreSQL RLS দ্বারা হার্ডওয়্যার-লেভেল ডেটা আইসোলেশন গ্যারান্টি।
- **নেতিবাচক:** কানেকশন পুলে প্রতি রিকোয়েস্টে টেন্যান্ট সেশন ভ্যারিয়েবল সঠিকভাবে সেট ও রিসেট করা নিশ্চিত করতে হবে।
